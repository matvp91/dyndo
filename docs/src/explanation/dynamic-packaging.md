# Dynamic packaging without media copies

dyndo separates stored media from the way that media is presented to a player. A CMAF source holds encoded samples and a segment index; a raw WebVTT source holds subtitle cues. A small descriptor points to those sources and holds presentation metadata. Manifests and responses are derived from them when requested.

This separation is what makes the system dynamic: changing the presentation does not require changing the media.

## Media bytes stay in their original objects

A conventional packaging pipeline commonly writes initialization segments, individual media-segment files, manifests, and sometimes separate output trees for different delivery formats. Storing those outputs alongside a fragmented MP4 source can duplicate media bytes already present in that source.

dyndo instead reads ranges from the original fragmented MP4:

```text
  CMAF source ── header read ──▶ track and segment model ──▶ manifest
       │
       └──────── requested byte range ─────────────────────▶ media response
```

For a CMAF source, the initialization segment and each served media segment are byte ranges inside the source object. Grouping fragments changes the boundaries of the range returned to the client; it does not create stored segment files. The server does not write generated output back to storage.

Raw WebVTT follows a different read path. dyndo reads the subtitle document and packages it as CMAF `wvtt` in memory. It can then return packaged subtitle segments or unpack them into WebVTT responses. These bytes are generated on demand, not copied from ranges in the `.vtt` file and not persisted as a second subtitle asset.

This has practical consequences:

- the stored media exists once;
- read-only storage is sufficient;
- adding a delivery format does not require another media tree;
- a CMAF source's `sidx` remains the source-fragment index from which served segments are derived;
- probing a CMAF source uses bounded header reads rather than reading the entire media object.

## Metadata is independent of encoded media

Information such as a track's language and role affects how a player presents a rendition, but it does not change the encoded samples. dyndo therefore stores that information in [`asset.json`](../reference/asset-json.md), where it can be corrected without touching the source object.

For example, changing an audio track from an undetermined language to Dutch or marking it as commentary changes the generated manifest immediately. DASH and HLS express those choices differently, but both render them from the same descriptor fields.

Track IDs derive from source paths rather than mutable metadata. A language or role correction therefore does not invalidate segment URLs or cached media.

## A request can choose a presentation

The descriptor supplies track metadata and default segmentation settings. Server options in the request path can override segmentation and choose output behavior, while the `filter` query parameter can narrow the tracks in a top-level manifest. Without writing new media objects, a request can:

- filter renditions by type, codec, bitrate, resolution, language, or role;
- group source fragments into longer served segments;
- introduce boundaries for splicing or period changes;
- render one DASH period or several;
- choose packaged `wvtt` or WebVTT documents for HLS;
- add a DASH thumbnail timeline and generate its JPEG sprites on demand.

Segmentation and output options live in the shared path prefix used by a manifest and its relative resources. A manifest filter is different: it only removes tracks from that manifest and does not prevent their URLs from being requested directly.

## Delivery formats are views, not stored layouts

DASH and HLS manifests are different descriptions of the same track and segment model. The protocol-specific crates decide how to group renditions, express roles, and write timelines or playlists. The media-serving path does not need to know which manifest led a player to it.

```text
                         ┌─ DASH MPD
  source + asset.json ───┤
                         └─ HLS playlists
                                  │
                                  ▼
                    shared init and media byte ranges
```

Some responses genuinely require generated bytes. A raw WebVTT source is packaged into CMAF `wvtt` in memory. Conversely, a text media segment can be unpacked into the WebVTT document referenced by the default HLS output. These conversions happen on demand and are not stored as another subtitle package.

## Operational benefits

- **Fewer invalidation problems.** Metadata documents and manifests are small; large immutable media objects can keep stable URLs and cache lifetimes.
- **Faster corrections.** Fixing a label, role, or selection rule does not wait for a media repackaging job.
- **Less pipeline state.** There is no generated segment inventory that must be kept synchronized with its source and manifest.
- **One descriptor contract.** The CLI writes the descriptor that the server reads, keeping indexed metadata and delivery configuration connected without making the CLI a manifest generator.
- **Storage flexibility.** The same descriptor model works over a filesystem or S3-compatible object storage through OpenDAL.
- **Incremental presentation changes.** Tracks can be indexed into a descriptor, relabelled, reordered, or removed without rebuilding unrelated renditions.

## Trade-offs

Dynamic packaging exchanges stored output for request-time work:

- source media must already be supported CMAF; dyndo does not transcode;
- manifest requests parse source headers and build track models;
- generated responses should be cached in a production deployment where the same URLs are requested repeatedly;
- moving a source without updating its descriptor breaks the path to it, while replacing a source with incompatible media can make probing or serving fail.

These trade-offs fit libraries that already have CMAF masters and value immutable media, inexpensive metadata changes, and avoiding protocol-shaped copies.
